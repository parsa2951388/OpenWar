# Open War Authentication — Architecture & Database Design

**Status:** Implemented in review branch; deployment gated on production resources and credentials  
**Target branch:** `open-war/auth-foundation`  
**Current deployment:** Cloudflare Pages proxy → Render `open-war-game`  
**Database discovery:** No Render PostgreSQL instance was found in the connected workspace.

## 1. Goal

Add recoverable Open War accounts with three sign-in methods:

1. Email + password (primary).
2. Google OAuth 2.0 / OpenID Connect.
3. Discord OAuth 2.0.

The system must retain the existing guest experience and preserve a player's current identity when a guest converts to a permanent account. The game should continue to use the existing persistent player UUID as the JWT subject; account IDs must not replace player IDs in game protocols.

This is an additive authentication layer, not a replacement of the game simulation, lobby, or WebSocket identity model.

## 2. What exists today

The selected self-hosting branch currently has:

- A master Express server and separate game workers.
- `registerSelfHostedApi(app)` in `src/server/SelfHostedApi.ts`, registered on the master server.
- A guest endpoint at `POST /auth/guest`.
- A stateless signed guest refresh token in the `__Host-openwar_refresh` cookie.
- Ed25519 access JWTs with a 15-minute lifetime and a public JWKS endpoint.
- `GET /users/@me` currently returns an empty guest identity and a minimal player profile.
- Existing client-side Google and Discord redirect entry points in `src/client/Auth.ts`, but their server endpoints are not provided by the self-hosted API.
- An existing email magic-link UI entry point; it is not email/password authentication.

The self-hosting guide explicitly documents that password login, Google/Discord OAuth, account linking, and recoverable accounts are not part of the standalone service yet.

## 3. Deployment and ownership boundaries

Keep the current request path:

`Browser → open-war-8o2.pages.dev → Cloudflare Pages Worker → open-war-game.onrender.com`

Auth routes remain on the master Express process (port 3000), not the game workers. The current nginx default route already sends ordinary paths to the master; worker-prefixed game routes continue to be routed to workers. The Cloudflare Pages Worker preserves method, body, cookies, and headers, so the browser continues using one origin.

Use a Render-managed PostgreSQL database in the same region as the game service (Frankfurt). Configure the service with Render's internal database URL, not a public URL, whenever the database and service share the Render region/workspace.

Do not place database credentials, OAuth client secrets, signing keys, or mail API keys in the client bundle or repository.

## 4. Database model

The initial schema is in `database/migrations/0001_authentication_foundation.sql`; replay-detection and OAuth browser binding are added by `0002_auth_session_replay_and_oauth_binding.sql`.

| Table                     | Responsibility                                                                                                                                |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth_accounts`           | Canonical account, normalized unique email, optional password hash, verification and account status.                                          |
| `auth_account_identities` | Google/Discord provider subject and verified provider metadata. Provider subjects, not email addresses, are the durable external identifiers. |
| `auth_account_players`    | One-to-one mapping from account to existing persistent player UUID.                                                                           |
| `auth_sessions`           | One row per device/session; stores only a SHA-256 hash of the opaque refresh token and supports rotation and revocation.                      |
| `auth_email_challenges`   | Hashed, expiring, single-use email-verification, password-reset, and email-change tokens.                                                     |
| `auth_oauth_transactions` | Short-lived OAuth state, nonce, PKCE verifier ciphertext, login/link intent, and validated return path.                                       |
| `auth_audit_events`       | Security-relevant account events without storing passwords, raw tokens, authorization codes, or full IP addresses.                            |

UUIDs are generated by the application. The migration requires no optional PostgreSQL extensions. Email normalization and password hashing are application responsibilities.

### Why account and player IDs are separate

The game's existing JWT `sub` resolves to a persistent player UUID. Player history, profile URLs, game joins, local settings, and other existing code already depend on that identity. The account UUID is an authentication/ownership record only.

When a guest registers or links a provider, the server verifies the current guest JWT and atomically attaches its persistent UUID to the new account. The UUID is never rotated as part of account creation. On a later device, the account's stored persistent UUID is used to mint the account JWT.

A persistent UUID already owned by another account must never be reassigned. Do not merge accounts merely because two providers return the same email address.

## 5. Authentication flows

### Email + password

- Registration requires the current guest access token, normalized email, and a password.
- Hash passwords using Node.js `crypto.scrypt` with N=32768, r=8, p=1 and a unique 16-byte salt. Never store or log plaintext passwords.
- Create the account, player mapping, initial session, and verification challenge in one database transaction.
- Send a single-use verification link. Until the email is verified, block password sign-in and account linking that relies on that email.
- Login returns the same generic failure for an unknown email and an incorrect password to avoid account enumeration.
- Password reset uses an expiring, single-use random token stored only as a hash. Reset revokes all refresh sessions and requires the user to sign in again.

### Google

- Use Authorization Code flow with OpenID Connect, server-side code exchange, state, nonce, and PKCE.
- Verify issuer, audience, signature, expiry, nonce, and the provider's `email_verified` claim.
- Use Google's immutable `sub` as `provider_subject`; email is profile metadata, not the identity key.

### Discord

- Use Authorization Code flow, one-time state, PKCE where supported, and server-side token exchange.
- Fetch the authenticated user from Discord's API and use its immutable user ID as `provider_subject`.
- Treat Discord email as verified only when the provider explicitly returns `verified: true`.

### Linking providers

- Provider linking requires an already authenticated account session and an explicit user action.
- The callback must revalidate the linking session and the OAuth transaction.
- If the external provider subject is already linked to a different account, reject the link. Never merge automatically based on matching email addresses.
- Account linking and guest conversion must be transactional and enforce database uniqueness constraints.

### Refresh and logout

- Keep the existing guest refresh path working for users who have not registered.
- For permanent accounts, issue a cryptographically random opaque refresh token; store only its SHA-256 hash in `auth_sessions`.
- Rotate the refresh token on every successful refresh using a compare-and-swap update. Reuse of an old token revokes its token family and requires a fresh login.
- Keep the current `__Host-openwar_refresh` cookie attributes: Secure, HttpOnly, SameSite=Lax, Path=/, and host-only.
- Access JWTs remain EdDSA-signed, issuer/audience-bound, short-lived, and continue to use the persistent player UUID as `sub`.
- Logout revokes the current database session. “Log out everywhere” revokes all active sessions for the account.

## 6. API contract

The following routes are the target contract; they are not implemented by this schema-only foundation.

| Method | Route                         | Purpose                                                                 |
| ------ | ----------------------------- | ----------------------------------------------------------------------- |
| POST   | `/auth/register`              | Convert the current guest identity to an email/password account.        |
| POST   | `/auth/login/password`        | Verify credentials and create a session.                                |
| POST   | `/auth/oauth/:provider/start` | Start Google/Discord login or link with PKCE and a browser-bound state. |
| POST   | `/auth/password/forgot`       | Send a generic password-reset response and email when applicable.       |
| POST   | `/auth/password/reset`        | Consume a single-use reset token and replace the password.              |
| POST   | `/auth/email/verify`          | Verify an email using a single-use challenge.                           |
| GET    | `/auth/callback/google`       | Complete Google OIDC authorization-code flow.                           |

| GET | `/auth/callback/discord` | Complete Discord authorization-code flow. |

| GET | `/auth/password/reset` | Redirect a reset-email link into the account modal with the single-use token. |
| POST | `/auth/refresh` | Rotate guest or account refresh state. |
| POST | `/auth/logout` | Revoke the current session and clear its cookie. |
| POST | `/auth/revoke` | Revoke all sessions and clear the cookie. |
| GET | `/users/@me` | Return linked identities and the existing player profile contract. |

All mutation routes need bounded request sizes, origin/CSRF protection appropriate to cookie-authenticated requests, per-route rate limits, strict Zod validation, no-store responses, and generic responses where account existence would otherwise leak.

## 7. Runtime configuration

Planned Render environment variables:

| Variable                  | Purpose                                                                        |
| ------------------------- | ------------------------------------------------------------------------------ |
| `DATABASE_URL`            | Render internal PostgreSQL connection URL.                                     |
| `DATABASE_SSL`            | Explicit production TLS mode if required by the selected connection endpoint.  |
| `GOOGLE_CLIENT_ID`        | Google OAuth client ID.                                                        |
| `GOOGLE_CLIENT_SECRET`    | Google OAuth client secret.                                                    |
| `DISCORD_CLIENT_ID`       | Discord application client ID.                                                 |
| `DISCORD_CLIENT_SECRET`   | Discord OAuth client secret.                                                   |
| `OAUTH_CALLBACK_BASE_URL` | Canonical callback origin, e.g. `https://open-war-8o2.pages.dev`.              |
| `EMAIL_PROVIDER`          | Email delivery adapter selection.                                              |
| `RESEND_API_KEY`          | Resend API secret used for verification and reset messages.                    |
| `EMAIL_FROM`              | Verified sender address.                                                       |
| `AUTH_ENCRYPTION_KEY`     | 32-byte hexadecimal key used to encrypt temporary OAuth PKCE material at rest. |

Existing `JWT_PRIVATE_KEY`, `JWT_KEY_ID`, `DOMAIN`, `API_BASE_URL`, and `SELF_HOSTED_AUTH` remain in place. All secrets belong in Render Environment settings, never in GitHub source or browser code.

## 8. Operational requirements

- Use a bounded PostgreSQL pool and set connection timeouts. Do not open one connection per request.
- Run versioned migrations before enabling account endpoints; migration execution must be serialized with a PostgreSQL advisory lock.
- Take automated backups before launch and test a restore.
- Keep OAuth callbacks and all authentication endpoints on the Pages public origin.
- Clean up expired OAuth transactions and email challenges periodically; retain audit events only for a documented period.
- Do not log Authorization headers, cookies, password inputs, OAuth codes, token values, reset URLs, or full IP addresses.
- Add alerting for elevated login failures, refresh-token reuse, database connection saturation, and email delivery failures.

## 10. Current implementation and deployment boundary

The review branch now contains:

- A PostgreSQL connection pool and serialized, versioned migration runner.
- Account/password registration and login using scrypt, email verification, password-reset request and completion.
- Google OIDC and Discord OAuth authorization-code flows with PKCE, state, browser binding, and verified provider identity.
- Account sessions with hashed refresh tokens, per-device session rows, rotation, logout, logout-all, and reuse detection.
- Guest-to-account conversion that preserves the existing persistent player UUID.
- Client-side account controls for the standalone guest panel, including Google, Discord, and email/password.

The branch is **not production-active**. No Render PostgreSQL instance exists in the connected workspace, no migration has been run against production, and OAuth/email provider credentials have not been configured. The existing live Render service still deploys `open-war/independent-self-host`; auto-deploy is disabled. Do not merge or switch the production service until the database, secrets, provider callback URLs, CI, and browser end-to-end checks are complete.

Render's free PostgreSQL tier is temporary and is not suitable for permanent player accounts. Use a paid database for production after approving the recurring cost. Keep all keys in Render Environment settings; never commit them.

The live guest session path remains unchanged and continues to serve players who have not created a permanent account.
